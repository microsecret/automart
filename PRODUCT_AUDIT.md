# Системный аудит «Авторынка»

Дата актуализации: 2026-08-10
Метод: статический разбор 60 API-маршрутов, Prisma-схемы и миграций, 46 страниц, 25 переиспользуемых компонентов, production-конфигурации и уже выполненных серверных проверок. Интерактивный browser-run временно недоступен в рабочем окружении, поэтому финальная визуальная матрица будет выполнена на сервере после публикации.

## Critical — блокеры для настоящего публичного запуска

### C-01. Денежный поток ещё не является лицензированным escrow

- Текущая реализация верно показывает счёт, получателя, квитанцию и подтверждение, но не удерживает деньги через лицензированного провайдера.
- До правовой, договорной и платёжной интеграции интерфейс и тексты должны использовать термин «сопровождаемая сделка», а не гарантированный escrow.
- Нужны: договорная модель, KYC/AML-процесс, сверка вебхуков, идемпотентность платежей, финансовый audit log и юридическая политика возвратов.

### C-02. Нет автоматизированного набора регрессионных тестов

- В `package.json` есть type-check, но нет unit/API/E2E тестов для прав, статусов, фильтрации и денег.
- Каждое изменение остаётся зависимым от ручного серверного прогона и может вернуть закрытые ошибки.
- Цель: добавить изолированные тесты для policy, lifecycle, фильтров, валидаторов и smoke E2E критических маршрутов без запуска тяжёлой сборки локально.

## High — текущий фокус реализации

### H-01. Роли — свободная строка, а policy распределены по роутам

- `User.role` — `String`, проверки `ADMIN`/`MODERATOR` повторяются в middleware и API.
- Это усложняет появление ролей партнёра, брокера и оператора, а также ревизию доступа к документам/платежам.
- Цель: enum ролей и единый слой `can(actor, action, resource)`; UI использует те же разрешения только как подсказку, сервер остаётся источником защиты.

### H-02. Нет полного сценария редактирования объявления

- Создание транспорта и запчастей есть, но нет защищённых API и экранов редактирования объекта объявления.
- Владелец может менять статус, но не исправить отклонённую карточку и не отправить её повторно на проверку.
- Цель: owner-only edit с разрешёнными полями по статусу, revision/audit event, повторной модерацией для существенных изменений и понятными формами в кабинете.

### H-03. Политика внешних изображений слишком широка

- Next Image принимает любой HTTPS-источник (`hostname: '**'`), что плохо контролируется с точки зрения privacy, расходов и доверия к медиаконтенту.
- Цель: whitelist собственного media storage и утверждённых аукционных доменов; импортёр нормализует URL, а фронтенд безопасно деградирует на placeholder.

### H-04. Password-вход нуждается в лимите попыток и едином anti-abuse контуре

- Telegram OTP защищён отдельными ограничениями, тогда как password provider полагается на базовую проверку учётной записи.
- Цель: per-IP + per-identifier rate limit, одинаковые нейтральные ответы и наблюдаемый security event без раскрытия существования email.

### H-05. Типы API DTO неоднородны

- В dashboard, admin, auctions и части деталей есть `any`, хотя доменные модели уже стабильны.
- Цель: выделить компактные DTO и type guards для публичных и кабинетных ответов, чтобы несоответствие данных ловилось до рендера.

## Medium — качество, масштабирование и визуальная полировка

- Перенос SQLite на managed PostgreSQL с бэкапами, мониторингом и репетициями восстановления остаётся обязательным до заметной нагрузки.
- Поиск запчастей работает по ORM-полям и кросс-номерам; для роста каталога потребуется PostgreSQL FTS/trigram и нормализованный каталог применяемости.
- `reactStrictMode` выключен; включить после устранения небезопасных side effects и добавить тест на отсутствие двойных запросов.
- Крупные client-компоненты и inline-стили ещё нуждаются в постепенном разбиении по экранам, а не массовой смене дизайна.
- Визуальная матрица 360/768/1024/1440 px и keyboard-навигация должны пройти после восстановления browser-run; текущие скриншоты пользователя остаются baseline для ручной сверки.
- Нужны HTTPS-домен, HSTS только после него, централизованные логи, error monitoring и health/readiness checks.

## Принятый порядок работ

1. Зафиксировать роли, permission-policy, lifecycle редактирования и защитные инварианты.
2. Реализовать owner-only editing с повторной модерацией и аудитом изменений.
3. Закрыть изображений/anti-abuse/DTO-разрывы и добавить быстрые регрессионные тесты.
4. Доработать каталоги, части, сообщения, delivery и auctions по одному сквозному сценарию.
5. Провести единый push, server build, миграции и HTTP/API smoke-проверку только в финале.

## Ограничения текущего рабочего прогона

- Локальные `build`, `tsc`, миграции и seed не запускаются по требованию владельца проекта.
- Пользовательская локальная `prisma/dev.db` изменена до текущей работы и остаётся вне staging/commit.
- Визуальный браузерный драйвер недоступен из-за ошибки среды; это не скрывается и не заменяется фиктивными скриншотами.
