# Repeated database lock, 22 October 2026

## Evidence and recovery

- Before the category artwork release, production remained on `8248bff5`.
- At 15:38 UTC, home returned 200 but the public database-backed catalog
  returned 500 after about 5.12 seconds. Active service status hid the outage.
- Prisma reported P1008 on unrelated listing and Telegram cleanup queries.
- `lslocks` identified Next PID 70542 holding a WRITE lock on the production
  database `/root/AutoMart/prisma/dev.db`; this was the automart MainPID.
- The inspected journal contains database timeouts from at least 07:00 UTC
  (12:00 Yekaterinburg), including Telegram upsert and fuel import operations.
  These failures do not establish which transaction originally retained the lock.
- Disk had 27 GB available; no build was running when the outage was inspected.
- Only `automart` was restarted. ActiveEnterTimestamp: 15:40:07 UTC
  (20:40:07 Yekaterinburg). The Telegram polling service remained active.
- Readiness then confirmed home, CSS and database-backed catalog HTTP 200.
  The public catalog returned 200 in about 0.097 seconds.

No database, journal, account, listing or polling offset was deleted, replaced
or restored. No journal-mode or credential change was made. The category
artwork had completed its isolated test run at 05:17 UTC, but had NOT been
promoted to production when this incident occurred.

## Unresolved

This is a recurrence of the 21 October incident, not proof of a frontend cause.
Restart is recovery, not a root-cause fix. The original retaining transaction
is still unknown. Trace long-running database work and concurrency before
changing database mode or transaction policy. The current readiness script
is a deploy gate, not a recurring runtime watchdog.

Anonymous session/home availability is not a completed sign-in test as the
affected user. The recovery checks did not impersonate a real account.

## Immediate recurrence and containment

After the category release, the smoke audit failed 10 checks (97 passed).
The new Next PID held both READ and WRITE locks and catalog requests again
returned 500. Therefore the earlier restart did not provide durable recovery.
No claim of successful final smoke verification is made for that run.

An ephemeral service override in `/run/systemd/system/automart.service.d/`
limits the existing SQLite URL to `connection_limit=1`, `socket_timeout=5`
and `pool_timeout=5`. It preserves the database file and existing EnvironmentFile.
Its reviewed template is `ops/automart-sqlite-pool.runtime.conf`. Remove only
that specific override after the equivalent application policy is deployed;
do not remove the existing environment/network drop-ins.

The application increment also shares Prisma on globalThis in production,
not only development, so separately bundled handlers reuse the same pool.
This reduces same-process connection contention; it does not serialize other
processes, add a distributed lock or prove which previous transaction hung.
The journal mode remains unchanged. A real-engine regression uses independently
loaded production-module copies and concurrent read/write transactions against
a disposable audit database only.

Verification before the application-policy release: eight policy tests passed;
the real-engine audit completed 240 concurrent read/write transactions and
all 120 expected writes, preserving journal mode and table readability.
The rebuilt application passed all 88 category UI/interaction checks.
With the temporary pool containment, the production smoke audit passed 107/107.
A separate read-only probe completed 24 production requests without HTTP errors;
its maximum latency was 9.371 seconds during a concurrent build. This is not
a sustained-load or long-term stability guarantee, and latency still needs work.
