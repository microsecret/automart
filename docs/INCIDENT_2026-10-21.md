# Database lock and account availability, 21 October 2026

## Confirmed evidence

- Production `automart` and `automart-telegram` were active. Static/home and
  unauthenticated session endpoints did not expose the outage.
- `/api/listings?limit=1` returned HTTP 500 after about five seconds.
- A separate read-only SQLite connection reported `database is locked`.
- `lslocks` identified the production Next process holding the database write
  lock. Prisma logged P1008 for unrelated catalog, Telegram and parser work.
- Disk space was available. No matching kernel OOM entry was found in the
  inspected incident window. The request/transaction that first retained the
  lock has NOT been established; do not attribute it to a particular feature.

## Recovery

At 05:09:55 UTC (10:09:55 Yekaterinburg), only `automart` was restarted.
No database, journal, user account or advertisement was deleted or restored.
After recovery, the catalog returned HTTP 200 in about 0.026 seconds locally
and 0.17 seconds through HTTPS. The database was readable (660 user rows).
The existing server smoke audit passed 107 checks, zero failures.
Sign-in and anonymous session endpoints returned 200; these do NOT constitute
a completed password/Telegram sign-in as the affected user.

## Prevention increment

`scripts/verify-or-rollback.sh` now checks the database-backed catalog status
and JSON contract, not just home HTML/CSS. It accepts an empty catalog as valid,
uses bounded HTTP timeouts and private temporary files, and has `--check-only`
for non-mutating diagnosis (no rollback or service restart).
Run `python3 scripts/test-release-readiness.py` on the application server for
the fake-HTTP regression cases. No production fixtures are created.
Server verification passed all four test methods (including invalid total
subcases), `bash -n`, and the live `--check-only` probe after the change.

This check is a deploy gate, not a recurring watchdog, and cannot prevent or
automatically repair a lock acquired hours after deployment.

## Remaining investigation

- Trace the transaction/request that held the write lock and bound its work.
- Production reports `journal_mode=delete`, despite an older deploy comment
  claiming WAL. No journal-mode change was made during incident recovery.
- Before considering WAL, inventory every SQLite engine (including Prisma's
  embedded engine), verify backup/restore procedures and patched versions.
  Python's server SQLite reports 3.45.1; version alone does not prove vendor
  backports. SQLite documents a WAL-reset race and fixed release versions:
  https://www.sqlite.org/wal.html#the_wal_reset_bug
- Validate real user sign-in after recovery without creating privileged
  sessions, modifying credentials or printing tokens.
- Unfinished QuickTour/UI changes are separate and were not released as part
  of this recovery.
