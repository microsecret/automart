# Продуктовая логика «Авторынка»

Этот документ — единый контракт между UI, API, модерацией и поддержкой. Пока целевые поля не добавлены в схему, он определяет направление последующих миграций и не должен расходиться с интерфейсом.

## 1. Участники и доступ

| Роль | Может | Не может |
| --- | --- | --- |
| Гость | Искать, читать публичные активные объявления, смотреть аукционные лоты | Видеть контакты, создавать сообщения/заявки, сохранять избранное |
| Пользователь | Создавать черновики, управлять только своими объявлениями, писать продавцу, вести свои сделки | Публиковать без модерации, менять чужие данные |
| Верифицированный пользователь | Получает бейдж и доступ к сценариям, где требуется подтверждённый телефон/Telegram | Не получает административные права автоматически |
| Партнёр по доставке | Работать только с назначенными заказами, выставлять счета/документы/события | Видеть сделки других партнёров или менять финансы без журнала |
| Модератор | Рассматривать очередь, одобрять/отклонять/приостанавливать, оставлять причину | Изменять финансовые реквизиты и роли |
| Администратор | Управлять модерацией, ролями, партнёрами и системными настройками | Обходить audit log |

Права проверяются на сервере для пары **actor + resource + action**. Скрытая кнопка не считается защитой.

## 2. Идентификация и вход

1. Пользователь может создать аккаунт по email/password; email должен быть подтверждён до чувствительных действий.
2. Telegram-бот связывает `telegramId` с номером только после передачи пользователем собственного контакта.
3. Вход по номеру: сайт принимает номер → бот отправляет одноразовый код только привязанному Telegram ID → код одноразовый, с TTL и rate-limit → создаётся сессия.
4. При конфликте email/телефона/Telegram аккаунты не склеиваются автоматически: пользователь проходит безопасное подтверждение, а система пишет audit event.
5. Неавторизованный переход в действие сохраняет `callbackUrl`, после входа возвращает ровно к исходному сценарию.

## 3. Жизненный цикл объявления

### Статусы

```text
DRAFT → PENDING_MODERATION → ACTIVE → PAUSED → ACTIVE
                  ↓              ↓       ↓
               REJECTED       SOLD    ARCHIVED
                  ↓
                DRAFT
```

| Статус | Видимость | Кто меняет | Обязательные данные |
| --- | --- | --- | --- |
| `DRAFT` | только автор | автор | минимальные данные можно сохранять |
| `PENDING_MODERATION` | автор + модерация | автор отправляет | категория, цена, описание, город, ≥1 фото для транспорта, владелец |
| `ACTIVE` | публично | модератор/автоправило | `publishedAt`, решение модерации |
| `PAUSED` | скрыто из поиска | автор/модератор | причина и источник |
| `REJECTED` | только автор + модерация | модератор | обязательная причина, возможность исправить |
| `SOLD` | в истории/карточке как продано | автор/модератор | дата продажи; новые обращения ограничены |
| `ARCHIVED` | только автор/админ | автор/система | причина архивации |
| `DELETED` | только audit/admin | система/админ | soft-delete, физически не удалять сразу |

### Правила публикации

- Одно объявление связано ровно с одним объектом: `vehicle` **или** `part`.
- Все поля валидируются по типу транспорта; нельзя сохранить «вариатор» для самолёта или `mileage` вместо `operatingHours` для спецтехники.
- Фото и документы проходят allowlist mime/size, антивирусную проверку на storage-слое и не публикуются до обработки.
- Изменение цены, VIN, категории, фото или описания после публикации создаёт revision и при необходимости повторную модерацию.
- Каждая смена статуса фиксирует `actor`, `from`, `to`, `reason`, timestamp и source.

### Проверки перед модерацией

- Для транспорта обязательны корректная категория, марка/модель, год, цена, город, состояние, доступный канал связи и минимум одно собственное фото. Для транспорта «на заказ» дополнительно фиксируются доступность, источник и ответственный партнёр.
- Система не допускает повтор VIN, повторную публикацию одного предмета, несовместимую категорию и признаки заведомо неверной цены. Автоматический сигнал не заменяет решение модератора.
- Отклонение всегда содержит reason code и короткое понятное объяснение: пользователь видит, что исправить, не теряя заполненные данные.

### Редактирование и ревизии

- Редактировать объект объявления может только владелец; модератор не подменяет данные продавца, а оставляет решение и причину.
- Для `ACTIVE` существенными считаются изменение категории/подтипа, цены, VIN, марки-модели, описания, фото и города. Такие изменения сохраняются ревизией и возвращают объявление в `PENDING_MODERATION`; карточка остаётся видна только до момента отправки обновления, если это разрешено политикой.
- VIN изменяется не более одного раза и всегда оставляет audit record. Год выпуска, марка/модель и пройденные проверочные документы после публикации требуют причины и повторной модерации.
- `REJECTED` редактируется и повторно отправляется владельцем; причина отклонения остаётся видимой в кабинете до следующего решения.
- Для каждого предмета может существовать только одно неархивное/неудалённое объявление: нельзя параллельно публиковать одну машину или одну запчасть дважды.

## 4. Каталог, поиск и избранное

1. Публичный поиск использует только `ACTIVE` и неистёкшие promoted listings.
2. URL — источник истины фильтров; UI синхронно обновляет query string и выдачу.
3. Модель доступна только после марки и только для выбранного типа транспорта.
4. Подтипы транспорта обязательны там, где они влияют на фильтры: кузов легкового авто, класс мото, надстройка грузовика, тип спецтехники, тип корпуса/мотора water, категория air.
5. Запчасти ищутся по названию, OEM, нормализованным кросс-номерам и совместимости; выдача всегда соответствует `partType` из URL.
6. Избранное доступно авторизованному пользователю, обновляется оптимистично и откатывается только после подтверждённой ошибки API.

### Идентификатор предмета по типу транспорта

Система не заставляет пользователя вводить несуществующий VIN ради единообразия формы. Дорожный транспорт (`CAR`, `MOTORCYCLE`, `TRUCK`) требует строгий 17-символьный VIN; для спецтехники допустим заводской/серийный номер, для водного транспорта — регистрационный номер или HIN, для воздушного — регистрационный/серийный номер воздушного судна. Значение проверяется на сервере, хранится в профильном поле и используется для антидублей. Поле `mileage` не заполняется фиктивным нулём для `SPECIAL`, `WATER` и `AIR`: у них используются моточасы или налёт.

## 5. Сообщения и безопасность общения

- Диалог создаётся с контекстом объявления и двумя участниками; отправитель не может писать сам себе.
- Сообщения доступны только участникам, лимитируются по частоте/длине и имеют статус прочтения.
- При `SOLD`, `ARCHIVED` или `REJECTED` новый диалог закрыт, существующий доступен в истории согласно retention-policy.
- Жалобы на сообщение или объявление создают модерационный case, а не удаляют контент бесследно.

## 6. Аукционы и прозрачная доставка

### Лот

`ACTIVE → RESERVED_FOR_INQUIRY → SOLD | EXPIRED | CANCELED`

- Импортёр хранит источник, дату проверки, валюту, фото и время торгов.
- Цена «под ключ» показывает состав: цена лота, курс/дата курса, комиссия, логистика, оценочные таможенные платежи. Не гарантировать итог, пока не получены документы.

### Заявка и доставка

`REQUEST_CREATED → DEPOSIT_REQUESTED → DEPOSIT_CONFIRMED → PURCHASE_IN_PROGRESS → EXPORT_PREPARATION → BORDER_AND_CUSTOMS → RF_CLEARANCE → LABORATORY_AND_EPTS → RUSSIA_LOGISTICS → READY_FOR_HANDOVER → COMPLETED`

Дополнительные статусы: `ON_HOLD`, `CANCELED`, `DISPUTE`.

- Каждый переход создаёт видимое покупателю событие с ответственным и следующим действием.
- Счета создаются отдельно по категориям; квитанция меняет статус на `AWAITING_CONFIRMATION`, а подтверждать её может только назначенный партнёр/менеджер.
- Документы имеют явную видимость (`BUYER_AND_TEAM`/`TEAM_ONLY`) и защищённое скачивание.
- Площадка не называет этот процесс escrow, пока деньги фактически не удерживаются лицензированным провайдером.

## 7. Модерация, партнёры и audit log

- Модератор видит очередь, историю revisions, жалобы и проверочные сигналы; решение всегда содержит reason code и человекочитаемый текст.
- Партнёр хранит организацию, ИНН, статус проверки и источник проверки. Автоматические данные внешних сервисов всегда имеют timestamp и fallback на ручную проверку.
- Audit log неизменяем: actor, entity, action, before/after diff, IP/session reference (минимизировано), createdAt.

### Матрица ролей

- Роли — закрытый набор: `USER`, `VERIFIED_USER`, `PARTNER`, `MODERATOR`, `ADMIN`. Неизвестное значение даёт только минимальные права пользователя.
- Правила доступа формулируются действием над ресурсом: например, `listing:update:own`, `listing:moderate`, `delivery:manage:assigned`, `payment:confirm:assigned`, `user:role:manage`.
- Проверка права выполняется на сервере до чтения чувствительного ресурса и до мутации; фронтенд лишь скрывает недоступное действие для удобства.

## 8. UI-состояния для каждого серверного действия

| Состояние | Поведение |
| --- | --- |
| Loading | Skeleton сохраняет геометрию экрана; кнопка показывает progress и блокирует повторный submit |
| Empty | Объясняет причину и предлагает релевантный следующий шаг |
| Validation error | Рядом с полем, с точной причиной и сохранёнными данными формы |
| 401 | Вход с `callbackUrl`; не показывать пустую выдачу |
| 403 | Ясно сообщить отсутствие прав, не раскрывать чужие данные |
| 404 | Понятный not-found + безопасный путь назад |
| 409 | Объяснить конфликт и предложить обновить данные/изменить действие |
| 429/5xx | Recovery state с retry, без потери набранного текста |
